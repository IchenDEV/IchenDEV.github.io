# AI办公真正缺的，是一层让软件适应人的编排引擎

---

## 一个越来越强烈的感觉

最近半年，我有一个越来越强烈的感觉。

AI 产品越来越强，软件却没有我们想象中那么自由。打开 Codex、Claude Code、WorkBuddy、千问办公，再看看现在大量 Agent 产品，里面已经塞满了东西。模型、搜索、浏览器、文件、Skill、Agent、自动任务、MCP、Computer Use。以前做不到的事情，现在很多都能做了。

可站在用户这边看，会发现一个很奇怪的问题：

**软件依然要求人适应软件。**

厂商决定聊天框长什么样，决定有哪些 Agent，设计几十个 Skill，准备一堆模板，再告诉用户：「你可以用 AI 完成很多事情。」用户确实拥有了更多能力，但用户自己的工作方式，依然很难真正进入产品结构。

我越来越怀疑，今天的 AI 办公大战，大家争的还主要是「给软件增加能力」。真正可能改变软件形态的那一层，还没有出现。

## Coding Agent 已经开始证明：统一的产品形态很难满足所有人

最近 Coding Agent 的变化很值得看。

Claude Code 已经支持 CLAUDE.md、Skill、Hook、Subagent、MCP 和插件。Hook 甚至可以在 Agent 生命周期中的特定节点强制执行脚本、检查命令或者补充 Context。换句话说，程序员已经可以相当深入地修改 Claude Code 到底「怎么工作」。

OpenCode 又往前走了一步。它把自己的 TUI 也做成了 Server 的客户端，底下有一个可以独立运行的 HTTP Server，外部产品可以直接调用 OpenCode 的能力。于是 UI 和 Agent Backend 被明显拆开了。你完全可以保留 OpenCode 处理模型、Session、工具和 Agent 的部分，自己重新做一套交互。

最近 DeepSeek Harness 更直接。它的核心设计理念就一句话：「Everything is a Plugin。」模型可以换，Tool 可以换，Skill 可以换，Session、Sandbox、Filesystem、Agent Loop、编排方式甚至 UI 都可以作为插件重新组合。

为什么程序员这么喜欢折腾这些东西？

很多时候并非 Claude Code 不够强。恰好因为它已经足够强，程序员开始对「工作方式」提出更细的要求。有人希望一个 Issue 对应一个 worktree，有人希望三个 Agent 同时工作，有人要求所有改动必须先跑测试，有人允许自动 commit 却绝对不允许自动 push，还有人需要左边放 Issue、中间看 Agent、右边实时看 Diff。也有人看到这些就头疼，只想打开 Terminal 输入一句话。

很难存在一套统一界面，把这些人全部服务好。所以程序员开始自己改。T3 Code 这种项目出现之后，连「重新做一个 Coding Agent 客户端」的成本都在下降。

这让我想到今年年初极客圈里出现的大量 AI 输入法。当底层能力足够便宜以后，人很自然会产生一个想法：「既然你的产品和我的习惯差一点，那我自己弄一个好了。」

Coding Agent 正在快速走到这个状态。以后很多程序员可能都会拥有自己的 Harness。有人真的自己写，有人 Fork，有人只是组合 Skill、Hook、插件和规则。形态不同，背后的原因很一致：

**统一的软件，越来越难覆盖每个人细碎又真实的工作习惯。**

## 今天的办公 Agent 依然主要在给用户准备更多积木

把视线从程序员移到办公市场，事情就有意思了。

Codex 现在已经有 Skills 和 Automations，可以让用户把一组工作方法保存下来，再按照时间自动运行。OpenAI 还在继续把 Codex 从代码场景推向报告、表格、演示、研究和各种知识工作。WorkBuddy 也已经把多 Agent、企业知识、会议 Context、Skills 和各种办公能力组织起来。腾讯今年发布的企业版本，重点已经从一个人调用 Agent，推进到团队和 Agent 一起工作。

这些方向都很有价值。可从更高一点的位置看，它们仍然很像：

```text
厂商准备模型 + 厂商准备 Agent + 厂商准备 Skill
+ 厂商准备模板 → 用户挑选和调用
```

过去是 App Store，现在越来越像 Agent Store 和 Skill Store。以前我要修图，就找一个修图软件；以后我要做投研，就找一个投研 Agent；我要处理招聘，就启用一个招聘 Skill；我要每天总结行业新闻，就增加一个自动任务。

AI 带来了非常大的能力提升，但产品和人的关系并没有完全改变。**产品依然提前定义了「你可能怎么工作」。** 而人的真实工作往往没有这么标准。

两个销售都用 Salesforce，工作方式可以完全不同。两个老板都看经营数据，一个每天只关心三个数字，另一个先看异常门店。两个 HR 都招工程师，一个特别看重 GitHub，一个先看公司经历。这些细微差别，不可能全部提前做成模板。

## 「养虾养马」已经开始靠近 Personal Harness，却依然需要用户自己养

OpenClaw 和 Hermes 这类产品让我觉得特别有意思，因为它们已经开始向另一个方向走。

OpenClaw 不只是聊天工具。它已经具有长期 Memory、Skills、Cron、Webhook、多 Agent、工具权限和多个交互入口。同一个 Agent 可以在不同渠道出现，记忆则持久化在自己的工作空间中。这已经很像一套个人 Agent 运行环境，模型只是其中一个部件，旁边还有记忆、工具、自动任务、Agent 和渠道。

为什么大家会说「养虾」？这个「养」字其实很准确。你慢慢给它装 Skill，给它接工具，让它记住自己的东西，改它的配置。时间久了，这只「虾」真的会和别人的不太一样。

Hermes 又往前走了一步。Nous Research 对它的定位甚至直接叫「self-improving AI agent」。它会从执行过的任务中形成 Skill，在以后使用这些 Skill 的时候继续修改，同时保存跨 Session 的个人信息和经验。这已经出现一个非常关键的变化：

```text
过去：用户配置 Harness → Agent 执行

开始出现：Agent 执行 → 总结经验 → 修改 Harness → 下一次继续使用
```

这条路很重要。相关研究也开始出现类似结果。Agent Workflow Memory 会从过去的任务轨迹里提炼可以复用的工作流，在 Mind2Web 和 WebArena 中都明显提高了任务完成率。2026 年关于企业任务程序记忆的研究，也开始直接研究「过去的工作方式能不能形成 Skill，再迁移到新的任务和模型上」。研究结果显示程序记忆确实能带来提升，同时也暴露出一个问题：从某个场景学出来的 Skill，很容易只适合原来的环境。

所以「Agent 会从工作中学习工作方式」已经不能算纯想象。只是今天还很早。OpenClaw 依然需要人花很多力气「养」，Hermes 已经开始自己学习 Skill，但离真正理解一个人复杂、含糊、充满例外的工作方法，还有很远。

## 真正的问题在于：普通用户根本不会设计自己的工作流

这里有一个很容易把整个想法推翻的问题。普通用户真的知道自己怎么工作吗？

我觉得答案挺有意思。**用户通常知道怎么做，却很难把自己怎么做完整地说出来。**

你问一个销售：「你筛选客户有什么规则？」他可能愣半天，然后告诉你：「也没什么规则，看情况。」

可你真的给他十封客户邮件，他马上就会开始判断：「这个马上回。」「这个没那么急。」「这个客户不要发模板。」「这个虽然金额小，但是老板介绍的。」「这个先问我。」

他不会写出完整的逻辑。事情真的出现以后，他知道自己想怎么处理。

这正好解释了为什么让普通用户自己搭 n8n 式 Workflow，很可能走不远。Trigger、Condition、Branch、Iterator，这些概念本身就是另一种编程。LLM 并没有自动消灭这种复杂度。

最近 HCI 研究也在验证这个问题。ALLOY 的研究发现，人在面对包含个人偏好的复杂任务时，很难通过 Prompt 一次性说清过程要求。研究者换了一种方法：让用户直接演示一遍操作，然后由系统把演示转换成可查看、可修改、可复用的 Workflow。在一个小规模用户实验里，这种方式比单纯 Prompt 更能捕捉人的过程偏好。

所以我越来越觉得：

**「让用户自己编排」这个方向没有问题，「让用户自己画工作流」可能从一开始就问错了。**

## 真正缺少的是一层看不见的编排引擎

假设一个运营每周一都会做一份销售报告。

第一周，他告诉 AI：「整理一下上周销售情况。」AI 做完。他说：「取消订单不要算。」「华东单独放。」

第二周又做。他说：「新店没有去年数据，不要算同比。」

第三周，他又纠正：「杭州上周有活动，这个增长不要解释成正常增长。」

半年以后，这个人可能一次 Workflow Builder 都没有打开。可是系统背后已经逐渐形成了一套东西：数据从哪里来，指标怎么算，什么情况算异常，哪些情况属于例外，什么时候自动运行，哪些地方需要确认，最终应该怎么展示。

用户没有在编程。他一直在工作。

**AI 在旁边把他的工作过程慢慢编译成软件。** 这就是我现在真正期待的那一层。它组合的内容应该包括：Model、Context、Memory、Skill、Tool、Agent、Workflow、Permission、Automation，甚至 UI。

UI 也很关键。今天大部分 Agent 最后还是回到一个聊天框。可老板每天早上真正想看到的，也许只是一个页面：「今天有三件事需要你决定。」下面一个合同，一个异常数据，一个 Offer。每件事情旁边只有「查看背景」「同意」「拒绝」。他根本不应该先输入一句：「帮我总结一下今天有哪些事情需要我处理。」

这个页面本身就是他的工作流。换一个老板，页面可能完全不同。

所以真正的 Personal Harness，最终修改的不能只有 Agent 怎么运行。**软件呈现在人面前的形状，也应该跟着工作变化。**

## 我认为 AI 办公下一场竞争，会从「增加能力」转向「让软件长成你的样子」

所以我现在对 AI 办公的判断已经越来越明确。

今天大家还在疯狂补材料。更多模型，更多 MCP，更多 Skill，更多 Agent，更多模板，更多自动任务。这些都需要。但这些东西很可能只是下一阶段的原材料。

真正缺少的，是中间那个「编译器」。它看着用户怎么工作，听用户怎么描述，观察用户怎么修改，记住用户在哪些地方拒绝、确认和例外处理，然后不断重新组织 Context、Skill、Agent、Workflow、权限和 UI。

程序员已经开始通过 T3 Code、OpenCode、DeepSeek Harness 和各种插件，手工做这件事情。OpenClaw 证明有人愿意「养」一个属于自己的 Agent。Hermes 又开始尝试让 Agent 自己学习 Skill 和用户习惯。这些都像是在往同一个方向靠近。

可面向普通办公用户的那个版本，我们还没有真正看到。

它也许不会叫 Harness。不会出现 YAML。甚至不会告诉用户自己有几个 Agent。用户感受到的应该非常简单：「这个软件越来越像我的软件。」

今天的软件公司先设计产品，再让几百万人适应同一套界面和流程。AI 给了我们一次把这个关系倒过来的机会。未来的软件，也许可以先提供模型和运行环境，然后在每个人每天的工作里，慢慢长成不同的样子。

所以我现在最关心的，已经不再是谁又发布了一个新的办公 Agent。

真正值得关注的问题是：

**谁能做出那层普通用户看不到的编排引擎，把「AI 能做什么」，慢慢变成「软件应该怎么为这个人工作」。**
