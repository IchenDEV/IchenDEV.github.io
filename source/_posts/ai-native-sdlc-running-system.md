# 代码变快以后，软件开发真正要升级的是运行系统

想象一家餐厅突然雇佣了十位出菜极快的厨师。过去需要十分钟的炒菜，现在一分钟就能端上柜台。然而，餐厅并没有因此快上十倍——门口依然排着长队，服务员在焦头烂额地确认忌口，传菜员正对着桌号发呆，而经理正忙着处理送错菜的投诉。当厨房的火力不再是瓶颈，原本被掩盖的交接、审核与验证，成了新的堵塞点。

这正是当前软件开发领域正在发生的剧变。Anthropic 最近描绘的 AI-Native SDLC（软件开发生命周期）图景，为我们打开了一扇观察窗。虽然行业尚未达成共识，但有一点已确凿无疑：当 Agent 将 Git、CI、测试、权限与监控这些零件串联起来时，软件团队的齿轮转动方式已经变了。

**“Code is no longer the bottleneck.”** 代码不再是瓶颈。真正决定一家团队交付速度的，开始变成目标能否说清、结果能否验证，以及风险能否被及时判断。

![软件开发真正要升级的是运行系统](/gallery/ai-native-sdlc-running-system/running-system.jpg)

## 当旧的交接撞上飞速的实现

在过去，一名工程师可能需要两周来磨出一个功能。在这段“漫长”的时间里，产品经理有足够的时间完善文档，测试人员有充裕的档期编写用例，安全团队也能慢条斯理地进行代码审计。

然而现在，Agent 可能在几个小时内就读完了整个代码库，完成了文件修改，补齐了测试并提交了 PR。人类的注意力并没有随之进化，于是等待开始发生在实现的前后。这就像刚才那家餐厅，厨师一分钟出菜，服务员却来不及确认桌号，验菜员也来不及检查过敏原。继续增加厨师，只会让出餐口堆满没人认领的盘子。

软件团队接下来的核心挑战，将从“如何写出代码”转向“如何管理注意力”——说清目标、传递上下文、验证结果、判断风险。整条交付链的效率，取决于最慢的那一环。

## Artifact：让交接不再只靠聊天和记忆

在忙碌的餐厅里，一张订单就是一份“Artifact”。它记录了顾客的特殊要求，指引着厨师的动作，也成了出餐核对的唯一凭据。如果菜出了问题，经理可以顺着订单追溯到是哪一步丢了信息。

在 AI 原生的软件开发中，Artifact 承担着同样的使命。它不再是生硬的文档，而是驱动 Agent 工作的“接力单”。

![交接不能只靠聊天](/gallery/ai-native-sdlc-running-system/handoff-artifact.jpg)

一个被确认的 `intent.md`（意图文档）可以自动启动方案设计；一份被批准的 `spec.md`（技术规约）可以激活实施计划；一次合并后的 PR 则会触发自动发布。在这个闭环里，信息不再是碎片化的聊天记录，而是可以被版本化、被审计、被机器理解的确定状态。

当然，我们也要保持警惕。Artifact 不会自动变成真理，过期的文档、冲突的规则、分叉的版本依然是陷阱。真正的提速，需要建立在明确的事实源、稳定的 ID 以及清晰的版本关系之上。

## 说明书、门锁与刹车

很多团队试图用一段长长的 Prompt 来约束模型，但这就像对着司机喊“请安全驾驶”，既无力又低效。一个成熟的驾驶系统，需要的是地图、红绿灯、安全带和刹车。

- **CLAUDE.md 像项目地图**：它简洁地勾勒出代码库的组织方式和团队约定，让 Agent 每次开工都能快速定位。
- **Skill 像驾驶经验**：它沉淀了 API 设计规范、品牌要求和常用套路，让 Agent 在遇到特定任务时能够“对号入座”。
- **Hook 与 Permission 则是红绿灯与刹车**：它们在文件修改或命令执行的瞬间进行检查，决定是放行、询问还是拦截。

![AI 需要说明书，也需要刹车](/gallery/ai-native-sdlc-running-system/manual-brake.jpg)

随着 Agent 的能力边界不断扩张，这些物理意义上的“门锁”比写得很长的 Prompt 更为关键。沙盒环境（Sandbox）限制了它的视野，MCP（Model Context Protocol）提供了标准插座，而权限控制则永远握在运行环境的手里。

## 用真实结果证明“已经完成”

厨师把菜盛进盘子，并不意味着任务结束。他需要尝一口味道，看一眼成色。Agent 的工作同样需要闭环。

![会自检的 Agent 更可靠](/gallery/ai-native-sdlc-running-system/self-check.jpg)

后端任务需要跑通测试与构建，界面任务需要截图对比，数据任务需要核对明细。这些判断依据必须来自真实的工具，而不是模型的“感觉”。

- **自我验证（Self Verification）**：执行者边做边查，修补机械性错误。
- **独立审核（Verifier Agent）**：另一位“评审员”拿着任务目标和证据重新挑错。

这种模式像极了驾校的“错题本”。当生产环境发生事故时，它会被转化为新的测试题，存入评测集。无论是更换模型还是调整提示词，这些曾经翻过车的地方，都必须重新通过验证。

## 从开发流程到个人工作系统

这套结构不仅仅适用于软件开发。如果我们把“写代码”换成任何复杂的脑力劳动，一个“个人效能系统（Personal Harness）”就浮现了。

![从开发流程到个人工作系统](/gallery/ai-native-sdlc-running-system/personal-harness.jpg)

当你对 AI 说“帮我更新融资材料”时，聊天不再是唯一的交互，而是目标的捕获器。系统会自动将任务拆解：市场调研进入 `research.md`，财务模型进入 `model.xlsx`，演示文稿进入 `deck.pptx`。

Verifier 会检查数据是否对齐，引用是否有效。当你确认通过后，这次工作的路径就被固化下来，成为下一次自动化的基石。在这里，聊天负责表达意图，Artifact 保存长期状态，Run 记录执行过程，而人，则保留最后的价值判断与授权。

## 结语

AI 正在将“生成代码”从一种稀缺能力变成一种基础设施。接下来的竞争，将发生在代码之外：目标如何被保存，权限如何被限制，结果如何被证明，失败如何被转化为经验。

让正确的信息，在正确的时机，以正确的粒度进入上下文。这听起来不像什么神奇的“念咒”技巧，但它正是我们从“使用 AI”转向“与 AI 共生”的关键所在。

我们终于可以少花点时间研究如何与 AI 斗智斗勇，而多花点时间，把工作本身想清楚。
